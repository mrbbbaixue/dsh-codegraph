# ADR-0005：索引生命周期（审批门禁 + 查询前自动 sync）

- 状态：已接受
- 日期：2026-09-14

## 背景

CLI 路径**没有 watcher**（ADR-0001 的代价）。`serve --mcp` 会起文件监听、写入后约 1 s 自动同步，CLI 单次调用不会。所以"索引什么时候更新"必须由插件显式补偿。

为定这个补偿方案，做了一组对照实验（2 文件的临时项目）：

| 改了什么 | 未 sync 时 `explore` 的表现 |
|---|---|
| 改了函数体（符号结构不变） | ✅ 返回**新源码**（`explore` 的源码段是从磁盘重读的），并带 banner：`⚠ Changed on disk after the last index sync: src/beta.ts ...` |
| 新增了一个符号 | ❌ 返回 `No relevant code found for "gamma"`——**没有 banner、没有报错**，就像这个符号不存在 |
| 新增文件 / 新增调用边 | ❌ 同上，静默不可见 |

**关键**：`explore` 的源码从磁盘重读，所以**内容变化**它能看见；但**图结构变化**（新符号、新文件、新边）必须靠索引，而 CLI 既不做 catch-up、也不给任何提示。

这条实测打掉了一个更早的假设——"靠 `explore` 自带的 staleness banner 兜底"。banner 只覆盖"已索引文件的内容漂移"，覆盖不了"新符号静默不可见"。而新增符号恰好是模型改代码时最高频的动作，后果是它会判定"这个函数不存在"。

`codegraph sync`（增量）实测 **409–535 ms**：干净状态 409/497 ms，有文件变化 535 ms——成本几乎全在**冷启动 + 全仓 mtime 扫描**，与有没有变化关系不大。（这个数字是 2 文件项目测的，大仓库会显著更高，未测。）

## 决策

**1. 查询前自动 sync。** `codegraph_explore` / `codegraph_node` 执行前先跑一次 `sync`。Config `autoSync` 默认**开**，可关。

**2. `init` / `index` 走审批，`sync` 放行。** 通过 `tools/pre-execute` 对 `codegraph_index` 的 `init` / `index` 两个 operation 返回 `ask` 决策（走 `ctx.approval` 一次性确认）；`sync` 不设门禁。缺审批服务时按 fail-closed 处理（拒绝）。

**3. 不自动 init。** 会话首次 `explore` 报未索引时，模型告知用户、由用户决定，不擅自跑全量索引。

## 理由

**自动 sync**：新增符号静默不可见这个盲区，恰好命中模型改代码时最常做的事。如果留着它，B1 提示词里 "trust codegraph's results — don't re-verify them with grep" 这句话就成了陷阱——模型吃一次"符号不存在"的亏就再也不信 codegraph 了，而这正是 B1/B2 要防的结局。400–500 ms 相对一次模型往返可忽略。

**审批门禁**：`ask` 是 dsh 的现成机制，比在提示词里写"请你先问一下用户"可靠得多（后者纯靠模型自觉）。它把"要不要建索引"的决定权交回给人，与官方 "indexing is the user's decision" 的口径一致，同时又不放弃自举能力。

**否决 TTL 去抖**：曾考虑"同一 root 30 s 内不重复 sync"来省掉连续查询的重复开销，但"改完文件立刻查"正好会撞上 TTL，盲区复现——在最需要 sync 的时刻跳过，等于没解决。

## 后果

**正面**：`explore` 的结果对模型**永远可信**，B1 里"别用 grep 复核"的指令才站得住；索引写入这个重操作有人的授权。

**负面**：

- 每次查询 +400–500 ms 起，大仓库未测，可能到秒级。`autoSync` 开关是这个风险的逃生阀。
- `tools/pre-execute` 的 `ask` 依赖 `dsh-user-approval` 在场；缺它时按拒绝处理，即 `init` 完全不可用（fail-closed 是有意的，见 dsh 的工具策略约定）。
- 自动 sync 是**写操作**（改 `.codegraph/`），即便增量也会更新索引文件。用户若把项目目录设为只读，`explore` 会连带失败——需要把 sync 失败降级为"继续查询但标注索引可能陈旧"，而不是让整个调用失败。

## 备选方案

- **不自动 sync，靠提示词让模型按需调 `index: sync`**：省掉每次查询的开销，但盲区保留，且依赖模型自觉。
- **插件自己起后台 watcher**：官方监听逻辑只能通过 `serve --mcp` 拿到，不开放复用。
- **首次查询时全量 `index`**：比 `init` 更贵，且与"不自动 init"矛盾。

## 修订记录

### 2026-09-15：自动 init，决策 3 作废

**起因**：用户要求「没有索引的话，要自动去生成索引」，并把「多大规模算太大」做成可配置项（默认 1 万个文件）。

**改了什么**：

- **决策 3（不自动 init）作废。** `codegraph_explore` 发现工作区没有索引时，插件直接跑 `codegraph init -y`，
  在同一次调用里把结果交给模型。理由与决策 1 同源：B1 要求「调研代码先 explore」，而未索引的工作区会让
  这条指令落空；「先报未索引、等用户点头、再查一次」把一次调用变成三次往返，还把决定推给了模型。
- **两道闸代替原来的「不做」**：`autoIndex`（默认开）与 `autoIndexMaxFiles`（默认 10000）。计数只遍历目录树
  （跳过点开头的目录与 `node_modules`），**超过上限立刻停止遍历**并返回说明文本，让模型走工具 + 审批那条路。
- **审批门禁保留，但只管工具调用**：模型显式调 `codegraph_index` 的 `init` / `index` 仍然 `ask`；插件自己
  发起的 init，授权来自用户在设置里的选择。
- **失败不静默**：`init` 失败会让那次 `explore` 报错并带上原因；同一个根目录上的并发查询共享一次构建。

**没变的部分**：查询前自动 sync；`sync` 不设门禁；`init` 传 `-y`；家目录与根目录仍然拒绝索引。

**新增的负面**：首次查询会包含一次全量索引，耗时由项目规模决定（1 万文件是缺省保护线，不是耗时承诺）；
关掉 `autoIndex` 就退回「报未索引 + 问用户」的老路径。
